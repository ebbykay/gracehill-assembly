# Persistent membership and attendance API
Migration 0007 creates households, members, attendance services and unique service/member attendance entries. The existing membership role is provisionally granted membership and attendance read/write; this role expansion requires organisational approval before real use. All routes require an active session and current roles, with exact origin checks for writes. Member and attendance changes use optimistic revisions and transactional success audit events. New attendance entries reject inactive members; existing entries may be corrected. Lists are bounded to 100 records or 500 attendance entries; pagination and aggregate counts are not implemented. Names, household associations and attendance may reveal religious affiliation, so no actual records are permitted until privacy, retention, lawful processing, access separation and operational security have been reviewed. No contact details or pastoral notes are collected. The public demo remains independent. Database runtime privileges are shared at application level, not row-level security. No delete endpoints. API paths: GET/POST /api/admin/households, /members, /attendance-services; PATCH /members/:id; GET /attendance-services/:id/register; PUT /attendance-services/:id/register/:memberId (relative to /api/admin). Revision zero creates an entry; positive revision updates it. Hosted migration, UI integration and full transactional store tests remain pending.
