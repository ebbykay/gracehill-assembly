# Administration requirements — draft
The current workspace is a design preview, not a functioning church management system. The existing prototype audit found illustrative member and financial figures, chart fixtures, alert-only actions and a client-side preview entry gate. These are not operational controls.

## Delivery gates
1. Approve module scope, data ownership, retention and access policies with church leadership.
2. Establish private deployment, server-side identity and permissions, session handling, audit logging and protected database.
3. Deliver programme and media editorial workflows first, with draft/review/publish and public-field allowlists.
4. Introduce membership and attendance only after privacy review; financial and pastoral records require separately restricted permissions and audit.
5. Test authorisation failures, backups and restore, deletion, accessibility and deployment rollback before accepting real records.

## Initial role proposal
Church leadership approves policies; content editors draft programmes and media; designated publishers approve public releases; membership clerks access assigned member functions; finance officers and pastoral care personnel have separately restricted access; system administrators manage identity and configuration. No role grants blanket access by default. All roles and permissions require approval.
